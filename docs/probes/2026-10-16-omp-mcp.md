# omp and the aos MCP server (agents that talk U6, first question)

Historical internal plan `2026-10-14-agent-communication`, D2/O4: "whether omp loads
an MCP server, and how it is registered, is U6's first question" (plan/orchestration not distributed)
· [Pi mechanisms](2026-10-14-pi-mechanisms.md)

Measured 2026-10-16 by agent-os-52 (Opus 5.5) on the Mac, offline: a Docker container of `aos-harness:laneq`
(`077d95c4d19b`, omp 18.8.3, its `aos-agent`) with `--network none`. omp talks to a fake OpenAI-compatible
model on the container's loopback (`fake_llm.py`, a custom provider in the agent directory's `models.yml`), which
logs the tool names of every request and can issue one tool call; a stub MCP server (`stub_mcp.py`) logs each
start and request. No worker credential, no sandbox, no bus. Kit: `scripts/openshell_probe/omp_mcp/`
(`probe.sh <image>`, about 6 minutes); the kit's run of every case: [kit-run.txt](2026-10-16-omp-mcp/kit-run.txt).
The omp flags are the runner's: `--no-extensions --no-skills --no-rules --no-title --approval-mode=yolo` and
the `--tools` allowlist of `agent_os/pi.py` (`OMP_TOOLS`), `PI_CODING_AGENT_DIR` and `HOME` as the runner sets them.

## Findings

1. **omp starts the server named in `$PI_CODING_AGENT_DIR/mcp.json`** (`{"mcpServers": {...}}`, stdio) under
   the runner's flags, with or without the allowlist: `initialize`, `notifications/initialized`, `tools/list`
   before the first model request. omp has no `--no-mcp` and no MCP flag; its MCP settings live in the agent
   directory's `config.yml` (`omp config set` writes there).
2. **Tool names.** omp registers a server's tool as `mcp__<server>_<tool>`, dropping the tool's repeated server
   prefix: the stub's `stub_ping` is `mcp__stub_ping`; aos-agent's six tools are `mcp__aos_ask`,
   `mcp__aos_reply`, `mcp__aos_inbox`, `mcp__aos_wait`, `mcp__aos_declare`, `mcp__aos_propose` (an unknown
   `--tools` name makes omp list every registered tool).
3. **A registered MCP tool is offered only when `--tools` names it.** Without an allowlist the model gets omp's
   default set (`read bash edit eval glob grep task wait todo web_search write`), with the runner's allowlist
   that set minus `task`; neither includes the MCP tool. Named in `--tools`, it is offered (the stub's, and all
   six aos tools). A `--tools` name that is not registered ends the run before any model request, exit 2,
   "Unknown tool in --tools".
4. **Startup window.** `mcp.startupTimeoutMs` (default 250) is how long omp waits for MCP discovery; 0 "waits
   until connections settle". Offline, both the default and 0 registered the tools in time; a slower start
   past the window would hit finding 3's exit 2.
5. **The repository's MCP files.** With the default config, servers in the working directory's `.mcp.json`,
   `mcp.json`, `.omp/mcp.json`, `.claude/mcp.json` and `.cursor/mcp.json` all start beside the agent
   directory's. When a repository server has the agent directory's server name, the repository's
   `.omp/mcp.json` wins and the agent directory's server does not start: a repository can replace the `aos`
   server. `mcp.enableProjectConfig: false` in the agent directory's `config.yml` stops all five; only the
   agent directory's server starts.
6. **Call timeout.** omp cuts an MCP tool call at 30 s ("MCP failure … failure: timeout … Request timeout after
   30000ms", returned to the model as the tool result). A server's own `"timeout"` (milliseconds) in
   `mcp.json` replaces it: with `"timeout": 1000000` a 130 s call completed. One `aos_wait` call lasts up to
   900 s (aos-agent's `WAIT_MAX`).

## What the runner does with it (U6, omp)

With `AOS_OPENSHELL_COMMS=1` and `AOS_OPENSHELL_PI_FLAVOUR=omp`: the run credential as for Claude
(`/sandbox/aos-run.json`, mode 600, never in the acceptance sandbox); `mcp.json` in the agent directory with
the `aos` server and `"timeout": 1000000` (finding 6); the six names in `--tools` (findings 2, 3), with `task`
among the others when agents are shipped; the omp paragraph in the prompt, which names the tools and asks for
`mcp__aos_inbox` at the start, before a commit and before the end, since no hook delivers messages and none
holds the stop. Every omp run, comms on or off, gets `config.yml` with `enableProjectConfig: false` (finding 5)
and `startupTimeoutMs: 0` (finding 4). The pi flavour runs with `--no-mcp` and stays unwired.

## Limits

The offline part had no sandbox, no OpenShell policy, no bus and no real model. The live proof is one run, one
omp version, on the Mac, against the operator only: no exchange with another agent, no proposal, no finish
notice to an omp parent (it would arrive at the next `mcp__aos_inbox`, with no hook). In the desk's ad hoc runs before the kit (not
repeated by it), a `.claude.json` in the project or in `HOME` and a `.vscode/mcp.json` with a `servers` key
started no server; omp names further sources (marketplace plugins, extension packages) not covered here.
